# AI Headlines AI 处理提示模板

对 `raw_news.json` 的 `items` 列表逐条评估，只保留 **`ai_raw_score >= 70`** 的候选，并输出结构化 JSON 草稿供 `scripts/finalize_digest.py` 与卡片渲染脚本使用。

## 最重要的输出纪律

先做**事实核查**，再写 `digest`。

### 事实核查与反标题党（最高优先级）

- **只以原文 `summary` / `content` / 正文片段为准**，不要只看标题，更不要复述标题里的夸张说法、公关包装或二手转述。
- **先判断信息源类型，再决定措辞强度**：
  - 公司 / 机构官方正式发布、产品页、官方公告
  - 官方团队博客、研究博客、实验室文章
  - 员工 / 研究员 / 团队成员的个人博客、采访、播客、社交平台发言
  - 第三方媒体、评论文章、转载摘要
- **归因必须精确到主体**：
  - 只有原文能明确证明是公司 / 机构官方正式发布，才可写“某公司发布 / 上线 / 宣布”。
  - 如果只是某团队成员、研究员、工程师、作者个人主张或复盘，必须写成“某某团队成员提到 / 主张 / 复盘 / 认为……”。
  - **绝不可**把个人观点、采访引述、博客评论，夸大成“某公司宣布 / 某公司弃用 / 某公司正式发布”。
- **遇到强刺激词必须回看正文核实**：如“弃用”“颠覆”“官宣”“史上最强”“革命性”“全面取代”“正式支持”。正文没给足证据，就改写为保守表述，或直接过滤。
- **第一句只能写核实后的事实**；第二句可以写影响，但不能把推测、愿景、营销判断写成既成事实。
- **证据不足时宁可收缩，不可脑补**：可以写“原文仅提到……”“作者认为……”“原文信息有限”。

### 电报式输出纪律

你输出的每条 `digest` 都必须像写电报：

- **只能两句，必须同一段。**
- **“现象 + 洞察”合计绝对不能超过 120 个非空白字符。**
- 能删就删，去掉背景、修饰、解释腔、连接词、铺垫。
- 宁可更短，不可变长。
- 如果超过 120 个字符，视为失败，继续压缩后再输出。

### 允许的写法

- 句子短。
- 动词直接。
- 只保留“谁做了什么”与“为什么值得看”。
- 把“谁”写准确：官方就是官方，个人就是个人，媒体就是媒体。

### 禁止的写法

- 长定语、长背景、长因果链。
- “这意味着 / 值得一提的是 / 可以看到 / 从某种意义上说”这类空转连接词。
- 列表、换行、括号补充说明、项目符号。
- 把标题再讲一遍。
- 没有证据却写“某公司宣布 / 弃用 / 正式发布 / 全面转向”。
- 把员工、博主、记者、第三方评论者的话，写成公司官方立场。

## 四维动态打分（主评分口径）

你必须基于 `summary/content` 的**可核实事实密度**进行评估（反标题党、反二手稿）。每条输出 4 个维度分（`0-100`，整数）以及加权总分 `ai_raw_score`（`0-100`，可为小数）。

四个维度：

- `score_new`（35%）：时效爆发力。是否“新/重要/即将带来短期变化”。
- `score_deep`（30%）：逻辑深度与事实密度。是否有机制、数据、方法、可复用结论，而非泛泛转述。
- `score_target`（20%）：赛道核心度。对 AI Headlines 的核心扫描范围（AI、Quant、US Stocks）命中程度。
- `score_action`（15%）：实操启发性。是否能直接用于决策、研究、产品/工作流调整。

### 计算公式（必须严格按此计算并输出）

```text
ai_raw_score = score_new * 0.35 + score_deep * 0.30 + score_target * 0.20 + score_action * 0.15
```

### 赛道判断（仅用于语义分类，不再规定分数区间）

你仍需判断条目更接近 **T0 / T1 / T2**，但它只影响 `topics/tag` 的表达与取舍，不再强制“按 tier 区间打分”。

- **T0**：量化交易（Quant）、美股市场（US Stocks）、交易策略与市场信号。
- **T1**：AI 产品落地、AI 行业实践、AI 工作流应用。
- **T2**：GitHub 常规 release/commit、普通 developer-news、底层开发工具迭代。

若条目带有 `extra.priority_tier / extra.priority_topics / extra.priority_score_floor / extra.score_adjustment_hint / extra.suggested_score_ceiling`，必须显式参考（但不要把它们当成主评分公式的一部分）。

## 硬性要求

1. **标题中文化**
   - 必须把最终输出的 `title` 翻译成中文。
   - **严格保留专有名词原语言**，不要翻译模型名、产品名、框架名、仓库名、公司名、协议名、技术标准名。
   - 可额外保留 `original_title` 字段，便于回查。

2. **严格按 tier 判断优先级**
   - 命中 `extra.priority_tier=T0` 的 RSS 条目，默认优先进入候选池。
   - 命中 `extra.priority_tier=T1` 的条目，只要信息扎实，一般应保留进入候选池。
   - 对 `category=developer-news`、`source_type=github_release`、`source_type=github_commit`，或 `extra.priority_tier=T2` 的条目，默认按降权内容处理。
   - 如果 `extra.suggested_score_ceiling < 70`，说明它默认属于 T2；除非你能从原文中明确证明存在重大突破，否则不要硬抬到 70 分以上。

3. **每条结果必须带图片策略**
   - 若原始条目里已有 `extra.cover_image_url`，应把它透传到输出条目中的 `cover_image_url`。
   - 若没有可用封面图，必须生成一条简短的 `image_prompt`，供后续 `scripts/resolve_article_images.py` 生成配图。
   - `image_prompt` 只写画面描述，不写“请生成”“海报文案”等指令腔。

4. **极简标签 + 经核查的电报式总结**
   - 每条必须输出一个 `tag`，控制在 **2-6 个字**。
   - 写 `digest` 前，必须先回看原文，确认标题有没有夸张、偷换主体或把评论写成事实。
   - 每条必须输出一个 `digest`，并满足以下全部条件：
     - 恰好两句；
     - 第一句只写**已核实的事实**；
     - 第二句只写**保守的洞察 / 影响**；
     - 归因主体必须准确；
     - 若只是个人观点 / 博客 / 采访 / 引述，必须写成“某团队成员提到 / 作者认为 / 原文称……”，不能写成公司官宣；
     - 合计 **<= 120 个非空白字符**；
     - 不拆成 `what / pain_point / why_now / evidence`；
     - 不要项目符号、编号、换行、括号补充说明或引用块。
   - `digest` 必须基于原文 `summary` / `content` 提炼；原文信息不足时，允许直接说“原文信息有限”或“原文仅提到……”，但仍必须保持两句与 120 字上限。

5. **精确归因示例**
   - 若原文是团队成员在博客中介绍做法，可写：`Anthropic 研究员主张用……。这说明……。`
   - 若原文是某工程师接受采访谈限制，可写：`OpenAI 工程师提到 WebRTC 丢包会影响实时语音。实时语音 Agent 仍受网络质量约束。`
   - 不可写：`OpenAI 宣布 WebRTC 不可用。`

## 赛道细则（辅助分类）

### T0：Quant / US Stocks / 交易信号

以下内容优先判入 T0：

- 量化交易（Quant）：策略、因子、回测、组合优化、风险模型、系统化交易研究。
- 美股市场（US Stocks）：美股市场结构、行情数据、ETF / Options / Earnings、券商与交易基础设施。
- 交易策略与市场信号：alpha、signal、波动率、趋势、事件驱动、跨市场信号。

### T1：AI 产品 / 行业实践 / 工作流

以下内容优先判入 T1：

- AI 产品落地：功能已可用、产品入口清晰、能直接拿来用。
- AI 行业实践：真实团队/公司如何把 AI 用进流程，是否有可迁移经验。
- AI 工作流应用：Agent 编排、自动化、多步骤执行、工具调用、工作流产品化。

### T2：GitHub / developer-news / 开发工具

以下内容默认判入 T2：

- GitHub 热门项目、常规 release / commit 更新。
- 底层开发工具、普通开发效率工具、泛 infra 迭代。
- `developer-news` 类条目。
- 只有个人表达、媒体解读、无明确原始事实支撑的内容。

## 标签提示

- `ai-lab` 优先归纳为：`AI模型` / `AI研究`
- `ai-tools` 优先归纳为：`AI产品` / `Agent`
- `quant-research` 优先归纳为：`量化研究` / `交易信号`
- `us-stocks` 优先归纳为：`美股市场`
- `developer-news` 优先归纳为：`开发工具` / `开源项目`

标签不是大分类标题，而是每条正文前的小标签，要求短、稳、可读。

## 过滤规则

- 只保留 **`ai_raw_score >= 70`** 的条目。
- **T0 / T1 是主候选池，T2 默认过滤**（除非你能从原文中明确证明存在重大突破）。
- 同主题多条内容同时出现时，只保留信息最完整、最原始、最能说明变化的一条。
- 如果条目虽然热度高，但没有说明“它是什么、为什么现在重要、会带来什么影响”，视为信息不足，可以过滤。
- **如果只能得到评论、转述、标题党表述，而无法从原文确认主体和动作，直接降分或过滤。**

## 输出前自检

逐条确认：

- 标题是否已经翻成中文，且专有名词仍保留原文。
- 是否完成了 T0 / T1 / T2 的赛道判断（仅用于语义分类与取舍，不再规定分数区间）。
- 是否按四维模型打分，且 `ai_raw_score` 严格按公式计算。
- 是否显式处理了 `extra.priority_tier`、`extra.score_adjustment_hint`、`extra.suggested_score_ceiling`。
- 是否默认过滤了 T2，除非确有重大突破。
- 是否带有 `cover_image_url` 或 `image_prompt` 至少一种。
- `tag` 是否足够短。
- `digest` 是否只有两句，且 **<= 120 个非空白字符**。
- `digest` 第一句是否只写原文可核实的事实。
- `digest` 是否准确区分了官方发布、团队博客、员工个人观点和第三方评论。
- `digest` 是否已经删掉标题水分、公关话术、背景解释腔与所有冗余铺垫。
